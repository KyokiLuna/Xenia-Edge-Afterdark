# Guide phase

The active order is guide, HDD/storage, profiles, avatars, XNA, Fake Live,
remaining system apps, then network apps. See the
[implementation roadmap](17559-roadmap.md).

This phase separates the existing host fallback from the installed 17559 native
HUD. A working fallback is needed while native guide support is developed; it
does not establish that the native HUD runs.

## Fallback controller routing

The baseline has two independent input-ownership problems:

- The outer SDL Guide poll reads guest `GetState`, whose buttons are neutralized
  while a menu/dialog owns input. Menu dismissal can consequently depend on its
  draw loop continuing to poll raw controller state.
- The menu keeps one previous-button mask and stops at the first connected
  controller. An idle controller in slot 0 prevents a controller in another slot
  from navigating or dismissing the menu.

The original single-controller Small Arms case already opens and closes the
menu. The stronger regression uses an idle virtual controller in slot 0 and an
active controller in slot 1: the old binary opens the menu but neither another
Guide press nor B dismisses it. Both controllers and their explicit slot
bindings are recorded in the private captures.

The repair gives SDL dismissal one owner, checks raw per-controller input, and
keeps unrelated dialogs and library navigation behind their existing ownership
guards. It also releases a closed menu's input blocker without waiting for
another guest-rendered frame. Menu navigation retains separate state per slot;
held close buttons must be consumed before input returns to the title.

The matched loop also exposed a Linux repaint race. The GLib idle callback can
clear its pending-source field before a background producer finishes publishing
the source ID, leaving a stale nonzero ID that suppresses every later paint.
Tracing observed that exact stale-source state. Registration, callback clearing
and destructor cancellation now share a mutex; the callback releases it before
calling window/presenter painting code.

## Native 17559 HUD: next engineering gate

The pinned baseline's source and installed-file inspection identified these
boundaries:

- Guide currently routes to the host context menu. `XamShowGuideUI`, guest
  SysApp registration/loading and system-app input ownership lack the native
  implementation needed by the installed HUD.
- `hud.xex` is a DLL. Replacing the foreground title with it would not implement
  an in-game guide. The installed skin is a resource DLL, not a foreground app.
- HUD registration and callback lifetime must be demonstrated. DLL attach
  success alone is insufficient: the inspected entry can return success even
  when registration has not succeeded.
- Exported XUI support currently covers strings, while HUD imports scene,
  focus and rendering functions. System graphics/device state and compositing
  are separate prerequisites; resource-file presence does not provide them.
- The native system app needs its own guest execution/input ownership while
  preserving the title process, executable module and controller state.

The smallest engineering gate is **HUD DLL attach → observed SysApp registration
→ validated guest callback dispatch → safe unregister/detach**, while keeping
the title intact. The full native acceptance gate then requires actual HUD
pixels over a running title, controller navigation, dismissal, and input/game
continuation in that same title. Neither gate is passed by the fallback repair.

The initial disassembler reported decompression warnings. A subsequent
independent LZX decode verified every compressed block's stored SHA-1 in the
supplied HUD and XAM images. The entire HUD text section matches the original
disassembly. Private `evidence/native-guide/sysapp-abi/` preserves the decode
records, instruction ranges and a readable ABI assessment; guest binaries and
their extracted data stay outside the repository.

## Native lifecycle implementation in progress

The common guest SysApp registry now separates prepared descriptors, callback
registration and initialized state. Requests pin a registration generation and
its module; unregistering or replacing a callback cannot redirect an old
request. Callback execution and module-reference destruction happen outside
the registry mutex. Shutdown stops normal admission and drains active
generations before destructive cleanup. The existing C++ app implementations
retain their buffer-copy/overlapped behavior; guest callback arguments are
opaque DWORDs and cannot safely use that wrapper.

The loader uses a system-process thread without replacing the foreground
executable. System DLL ownership is set before module publication, excluding
the HUD from title-process DLL notifications. Initialization message
`80000004` receives the verified 16-byte packet (primary/secondary flag,
options pointer, module handle, launching user index) and a writable output
DWORD. Shutdown sends `80000003`, drains callbacks, then sends `80000005` and
unloads the owner. Repeated and deferred unload requests share one claim.

The default-off `native_guide_bootstrap_probe` is a diagnostic for those
returning lifecycle callbacks. It is not a native-guide mode. It does not
exercise UI waits, asynchronous title transitions, guest XAM task TLS or the
guest loader's image-reference/count protocol. Those need explicit lifecycle
support before using the path for general system apps. The isolated capture
runner supplies the diagnostic's process deadline. In-process callback calls
retain their caller's context; guest system-process/overlapped dispatch returns
`E_NOTIMPL` until its system execution and request ownership are implemented.
The existing C++ system-app dispatch paths retain their behavior.

Verified message `80000009` saves a 0x480-byte HUD state snapshot. Message
`80000008` creates its UI and borrows a real XUI drawing context from its caller;
passing a guessed packet or null context is unsafe. The latter path registers
classes, creates the root and scene, enables system-app input and navigates to
that scene. An executing render/update loop and compositing remain necessary
after scene creation. Initialization success alone cannot establish any of
these rendering or input results.

The first actual lifecycle capture used native ELF `391757fe...` and run
`20261103T210400Z-native-guide-bootstrap-391757fe-6b1ibjil`. HUD registered
callback `913E5930`; initialization returned 0 with output `00000480` (1,152
bytes), close/destroy returned 0, and the foreground executable stayed intact.
Inspected screenshots show Small Arms continuing to its title screen. The run
also called undefined `XMemSet` twice and undefined `GamerCardStartup` once
during initialization. Cleanup called undefined gamer-card, XUI unregister and
system-input functions. This establishes real callback execution, while leaving
functional initialization blocked by those dependencies.

The trace led to actual implementations of `XMemSet`, `XMemCpy` and
`XMemCpyStreaming`. Their argument order and destination-pointer return are
verified against the supplied XAM; zero count does not access the pointed-to
memory. Streaming copy shares the byte-copy contract; overlap preservation and
console cache-timing equivalence are not promised. No supplied schema blob or
firmware addresses are embedded in the implementation.

## Follow-on input review

Actual packaged navigation exposed two further ownership problems. A stationary
pointer or ImGui's older navigation ID could overwrite the menu's selected
action. Both actual-action regressions failed before the hover correction and
passed afterward. Subsequent runtime still missed some startup navigation:
Up/Down/A were sampled only in Draw, while Guide/B dismissal used the independent
SDL poll. The first eight-Down sequence opened Profiles instead of Return; a
later sequence reached Return after startup. These results are recorded as
mixed, not as a passed scripted confirmation sequence.

The SDL path now delivers raw menu edges and held-direction repeats from its
16 ms poll to the UI thread. The menu's SDL mode does not also poll during Draw;
legacy draw polling remains available to other callers. Custom menu navigation
has one activation owner, with mouse, keyboard and controller paths checked
separately. Real pointer movement can take focus. Independent ImGui navigation
cannot activate a different menu item.

Menu creation/closure and ImGui dialog ownership each have a generation. Queued
input is discarded after either changes; a shared lifetime token is checked
before accessing the window. Dialog add/remove changes the capture generation
even when a modal opens and closes without a Draw. First-popup rebasing avoids
discarding valid input merely because the menu has not drawn yet. Held buttons
across ownership changes stay consumed until release or a real new edge.
Native wx modal ownership remains checked at delivery; it does not have the
same generation tracking, and unobserved raw popup round trips remain a limit.

The actual menu-to-confirmation test covers external input before a new ImGui
frame and ordinary ImGui controller navigation. Thirty held-A frames must not
confirm; release and a fresh A must confirm exactly once. A window-wide
navigation-disable flag broke the next dialog's fresh-A handling in the matched
test. The fix uses item-level navigation ownership and records controller
modality without changing confirmation-dialog behavior.

Latest direct suites: base 84 cases / 2,287 assertions; network 124 / 11,169;
kernel 59 / 2,127; VFS 14 / 218; UI 28 / 267. All **309 cases / 16,068
assertions** pass. The private `poller-fix-build/status.json` preserves the exact
commands, binaries, source snapshots and historical failed checks.

## Remaining native guide boundary

Two corrected-memory HUD lifecycle cycles returned initialization output
`00000480`, close/destroy success and `retired=true`, preserving the foreground
title. A packaged return to dashboard also executed full in-process kernel
teardown and relaunch, followed by two more HUD lifecycle cycles. Ordinary
window close uses the existing quick-exit path and does not independently prove
full teardown.

Native scene/render acceptance remains blocked. Verified XUI shared-renderer
initialization needs a guest D3D device, a 0x7C-byte parameter block and a texture
loader callback; drawing-context creation produces a real guest object with
graphics resources. The lightweight/shared and normal device factories are
different paths and must not be conflated.

The common graphics boundary needs further work before enabling native guide
rendering beside a title. Deferred PM4 interrupts retain a CPU mask and GPU
submission, but no verified title/system owner. The current global callback/data
pair is resolved at delivery, and graphics DPC execution forces title context.
Routing must retain existing title/boot behavior, preserve GPU-completion order,
and identify ownership at submission before selecting a callback generation.
Neither CPU masks nor a nonzero system-device pointer establish that ownership;
broadcasting completion to both devices would be incorrect. Boot entry threads
default to title context, but actual guest-worker graphics ownership remains
unverified. No speculative interrupt routing or guest D3D initialization was
introduced by this package.

Gamer-card startup/cleanup, XUI classes/scenes/rendering, system-app input,
guest XAM task context and the public ShowGuide request path also remain
incomplete. No native HUD pixels, native multiuser guide navigation, native
friends/invitations/parties/voice or macOS execution are claimed. Work stays in
the guide phase; HDD work has not started.
