Avatar-family XAM export -> message-port command table
=========================================================
Derived by disassembling $flash_xam.xexp (the retail, depatched xam.xex)
with Capstone (PPC64BE), starting from the export table
(reference/exports/flash_xam.xexp.exports.txt). See
_avatar_disasm/avatar_disasm_full.txt for the raw disassembly this was
read off of, and _avatar_disasm/disasm_avatar.py to redo/extend it for
other ordinals.

Almost every XamAvatarXxx export just marshals its arguments into a stack
buffer and calls a shared helper at 0x818d2470 (or occasionally sends
directly), which does:
    li r3, 0xf3
    bl 0x818fd2d8      ; XMsgStartIORequestEx-equivalent dispatcher
i.e. "send a message to system-app port 0xf3" (this is the Avatar system
app / avtr.xex-equivalent - not present as a standalone file in this dump).
The low 16 bits of the command word (upper 16 bits are always 0x6000,
i.e. commands are 0x6000XX) are listed below per export.

Observed system-app message ports (not confirmed against real names, just
grouped by what shares a port in this disassembly):
  0xf3  Avatar system app - almost all XamAvatarXxx calls
  0xfe  Shell/UI launcher - avatar-related UI show/launch calls (mini creator,
        awards UI, "missing avatars" UI)
  0xfb  Something profile/asset-enumeration related (XamUserValidateAvatarManifest,
        XamUserCreateAvatarAssetEnumerator) - not further identified

UPDATE (corpus-wide IPC work, see 06_IPC_SERVICE_MAP.txt / 08_STRUCTURES.txt):
this table's "dispatcher" addresses (0x818fd2d8/540/548/5b8 and the shared
helper 0x818d2470) are xam.xex's OWN internal implementations - xam.xex
doesn't need to import these since it provides them. Other modules that
import the same functionality do so via named imports, now confirmed:
XMsgStartIORequestEx, XMsgStartIORequest, and XMsgInProcessCall (see
reference/imports/flash_dash.xex.imports.txt for a live example). This
confirms 0x818fd2d8-family really is "the XMsgStartIORequestEx-equivalent"
as this table already assumed, just now backed by cross-module evidence
rather than only the naming already present in xam_avatar.cc's comments.
The 0xfb port is still not semantically named, but the corpus-wide scan
found it reused by $flash_dash.xex too (commands 0xB0019/0xB003D) - see
06_IPC_SERVICE_MAP.txt for more samples if you want to keep narrowing it
down.

How to extend this table
-------------------------
1. Look up the ordinal in xenia-edge/src/xenia/kernel/xam/xam_table.inc to
   get more names if you need other (non-avatar) XAM functions.
2. Find its address in reference/exports/flash_xam.xexp.exports.txt
   (or any other module's .exports.txt).
3. Re-run: python3 _avatar_disasm/disasm_avatar.py \
     "$flash_xam.xexp.header" "$flash_xam.xexp" 0xORDINAL 0x81870000
   (0x81870000 is xam.xex's load address - reuse it for any $flash_xam.xexp
   ordinal since the patch doesn't relocate.)
