6. [RESOLVED] Command-word decoding stops at "port" for INFERRED IPC entries
-------------------------------------------------------------------------
Original text (kept for history): the automated IPC scan used to record
only the message PORT, not the 0x6000XX-style COMMAND word.

RESOLUTION: build_06_ipc.py now decodes the command word too, via
disasm_support.py:resolve_register_value_before (backward dataflow through
li/lis+ori/lis+addi/mr chains, including the cross-register
`lis r11,HI; addi r5,r11,LO` address-formation idiom a first attempt at
this missed). Classification of "leaf dispatcher" vs "helper" was
rewritten as a two-pass bootstrap (see build_06_ipc.py's docstring) after
a length-based heuristic first attempt mis-flagged a generic register-save
prologue helper as a dispatcher. The decoder is cross-validated against
every CONFIRMED avatar entry on every run (see the top of
06_IPC_SERVICE_MAP.txt for the live count) - currently 23/23 exact matches
(started at 22, +1 after XamAvatarWearNow was hand-verified and promoted -
see item #7 below).

That validation process caught two pre-existing transcription bugs in this
corpus's own CONFIRMED_AVATAR table (not in the decoder): XamAvatarLoadAnimation
and XamAvatarBeginEnumAssets had their VAs transposed, and
XamUserGetUsersMissingAvatars' command word was mistranscribed as 0x3000a
instead of the correct 0x2300a (a `lis r4, 2` was misread as loading 0).
Both are now fixed in build_06_ipc.py's CONFIRMED_AVATAR table and
02_AVATAR_COMMAND_TABLE.txt.

Remaining gap: PORT_VALUE_MIN (0x80) is itself a heuristic cutoff chosen to
separate real port values (0xf3/0xfb/0xfe/0xfa/0xfc/0xff, all observed in
the top quarter of the byte range) from common small-integer false
positives (li r3,0 / li r3,1 flags) that flooded results on non-XAM
modules like AvatarEditor.xex before this cutoff was added. A real port
below 0x80 would currently be missed - none has been observed yet, but
this is a real limitation, not a proven-safe assumption.

8. [PARTIALLY RESOLVED] Call-graph coverage extended for low-export modules
-------------------------------------------------------------------------
Original gap: call-graph/string-xref coverage was exported-functions-only,
which found almost nothing for application-style modules with few/no
exports (gamerprofile.xex: 0, createprofile.xex: 2, signin.xex: 0, etc.).

RESOLUTION (partial): build_04_calls.py now also does a capped (250
functions) breadth-first walk of internal `bl` targets starting from each
low-export module's entry point (disasm_support.py:discover_functions_bfs),
PLUS an opportunistic one-hop expansion that follows function-pointer
arguments passed to *Register*-style import calls (e.g.
XamRegisterSysApp's callback argument - see
build_04_calls.py:find_callback_roots) - this is exactly the
"repeatedly-seen internal helper" pattern this item originally called out,

Coverage went from 6/47/601 (exported/BFS functions/edges) to
2440 exported + 634 BFS-discovered functions, 13878 edges, across all 14
PRIORITY_MODULES (previously only 6 modules had any coverage at all).

Remaining gap (AT THE TIME this item was written): this was still bounded
(250-function cap per module, one hop of callback-pointer following) and
did NOT expand string-xref coverage into BFS-discovered functions
(build_05_strings.py only computed xrefs against exported-function
disassembly) - a string referenced only from a BFS-discovered internal
function wouldn't show an xref. Also, dash.xex/AvatarEditor.xex are large
enough that the 250-function cap only reaches a small fraction of their
real code from the entry point alone.

RESOLUTION (string-xref part, later pass): build_05_strings.py's
compute_xrefs() now reuses build_04_calls.discover_module_functions() -
the SAME function set (exports + BFS-discovered internals + callback
descendants) the call graph and IPC scan use, not a separate export-only
walk - so a string referenced only from inside a BFS/callback-discovered
function is now found. This surfaced (and then required fixing) a real
bug in the matching logic: the `lis rX,HI` + `addi rD,rA,LO` /
`la rD,LO(rA)` address-formation idiom was being checked against the
WRONG operand (the destination register `rD` instead of the source
register `rA`, which is the one that actually has to match the `lis`
target - `rD` is frequently a DIFFERENT register, e.g.
`lis r11,HI; addi r7,r11,LO`). Only the self-referencing `ori rX,rX,LO`
idiom happened to match under the old (wrong) check, which is why a
first attempt at this reuse regressed to just 1 function corpus-wide with
any xref (verified: 0 xrefs even for a known-good hand-picked address in
xam.xex). Fixed by comparing operand[1] (source) for addi/la and
operand[0] (destination) only for the genuinely self-referencing `ori`
case. After the fix: 9 distinct functions across 5 priority modules show
at least one real string xref (spot-checked, not just count-checked -
e.g. XamGetDefaultImage -> "defaultsystemimage.png",
XamContentCreateEnumerator -> "XSYSLAUNCH:\", both clearly correct
semantic correlations). This is still a bounded heuristic (adjacent
`lis`+`addi/la/ori` PAIR match only, exact-VA match only - a candidate
address landing a few bytes off a string's start, e.g. into padding
before it or a table-entry pointing near-but-not-at a string, is a
genuine miss, not a bug; several such near-misses were observed and are
NOT counted as xrefs) - a low true xref count is expected and is not
itself evidence of a remaining bug, given how narrow the matched
instruction shape is relative to all the ways PPC code can form an
address (TOC-relative loads, computed offsets, etc. are NOT covered).

Remaining gap (still open): does NOT cover other address-formation idioms
(indexed/computed addresses, loads through a pointer table, etc.) - only
the direct 2-instruction lis+{addi,la,ori} pair. raise BFS_CAP for
specific high-value modules if still needed for call-graph reach; further
xref-idiom coverage should stay opportunistic (only if a specific known
string reference is confirmed missing), not a blanket rewrite.
Priority/value: LOW-MEDIUM - the highest-value instances (avatar's
0x818d2470, gamerprofile's SysApp callback) are already covered; further
expansion is diminishing returns without a specific new target function.

9. [RESOLVED] IPC classification rewritten from heuristic leaf/helper/fixed
   to statically-proven endpoint-reachability chains
-------------------------------------------------------------------------
Original gap (see items #6/#7 above for the full history of the
leaf/helper/fixed classifier they describe as "resolved" at the time):
that classifier only handled 0-hop ("leaf") and 1-hop ("helper"/"fixed")
dispatch shapes, hardcoded promotion of ANY `li r3,port-shaped-value;
bl target` candidate straight into ipc.tsv without proving `target`
actually reaches a real XMsg* endpoint, and recorded only ONE IPC callsite
per function (a `break` after the first match), silently dropping
functions that dispatch different commands on different branches.

RESOLUTION: build_06_ipc.py was rewritten around an endpoint-proof
architecture (see its module docstring for full detail):
  - every `li r3,port;...;bl target` occurrence is now kept as its own
    candidate (module, caller_va, callsite_va) - no more one-per-function
    cap; 6 functions in the current corpus have >1 retained IPC callsite.
  - a per-module endpoint registry is built from that module's own
    exports/import-thunks whose real (ordinal-database-resolved) name
    starts with "XMsg" - never hardcoded to a fixed function list.
  - disasm_support.find_endpoint_chain does a bounded BFS (depth<=4,
    node_cap<=40) over `bl` targets from each candidate looking for ANY
    path to a registered endpoint. No path found -> candidate stays in
    _ipc_candidates.tsv only, confidence=CANDIDATE, status
    UNRESOLVED_NO_ENDPOINT or ENDPOINT_FOUND_BUT_ARGS_UNRESOLVED - NOT
    written to ipc.tsv/06_IPC_SERVICE_MAP.txt. Path found -> promoted to
    DERIVED, with the full hop-by-hop evidence_chain recorded (not
    flattened into a single vague "dispatcher").
  - resolve_ipc_args() generalizes the old 0/1-hop-only arg resolution to
    arbitrary chain depth, walking hop-by-hop via
    resolve_register_value_before (falls back to trace_incoming_register
    to alias to the calling hop's own parameter and recurse toward the
    original caller). Produces command_source/port_source in
    {CALLER_CONSTANT, FIXED_WRAPPER, FORWARDED_ARGUMENT, COMPUTED_WRAPPER,
    UNKNOWN} - see build_06_ipc.py's docstring.
Result on this corpus: 23 CONFIRMED (unchanged - still hand-verified) +
256 DERIVED (endpoint-proven, up from the old classifier's less-rigorous
INFERRED set) = 279 entries; 91 candidates REJECTED for lacking endpoint
proof, including every named false-positive this rewrite specifically set
out to catch (XamUserCreateStatsEnumerator -> XamCreateEnumeratorHandle,
SetFilePointer/SetFilePointerEx -> RtlSetLastError,
XuiSceneNavigateForward -> XuiElementGetFocusUser,
XamProfileOpen -> XamContentCreateInternal,
XamBackgroundDownloadSelectDevice -> XamContentCreateDeviceEnumerator,
XamProfileCreateEnumerator/XamContentCreateEnumeratorInternal/
XamContentAggregateCreateEnumerator/XamContentCreateDeviceEnumerator, all
verified via _ipc_candidates.tsv to show UNRESOLVED_NO_ENDPOINT). The
chain-proof engine is re-validated against all 23 CONFIRMED entries on
every run (23/23 matched, 0 mismatches at time of writing) before any of
its DERIVED output is trusted.
Items #6/#7 above are kept verbatim as historical record of the PRIOR
(now-superseded) classification mechanism and the hand-verification work
that fed into CONFIRMED_AVATAR - none of that hand-verified ground truth
changed; only the automated classifier around it did.
Priority/value: this was the highest-priority item in the most recent
cleanup pass (see the "SEPARATE IPC CANDIDATES FROM PROVEN IPC" /
"CRITICAL COVERAGE BUG" / "IPC EVIDENCE CHAINS FIRST-CLASS DATA" spec
items) - now resolved. Semantic naming of non-avatar DERIVED command
words remains open (see item #7's "what would resolve it further").

10. [RESOLVED] build_11_validate.py silently undercounted strings.tsv rows
    (csv module's default quoting swallowed rows containing '"')
-------------------------------------------------------------------------
What was wrong: VALIDATION_REPORT.txt's "strings indexed" coverage figure
read 40907 while strings.tsv actually had 43670 data rows (confirmed via
`wc -l`) - a silent ~6% undercount, discovered while expanding
build_11_validate.py with the semantic checks in item #9. Root cause:
read_tsv() used Python's csv.DictReader with its default
quoting=QUOTE_MINIMAL, which treats a bare `"` character as the start of
a quoted field and will consume subsequent newlines into that field until
it finds a closing quote (or EOF) - these TSVs have no quoting/escaping
convention at all (plain tab-delimited, raw string/text content written
as-is), and 963 lines in strings.tsv contain at least one `"` (e.g.
literal quote characters inside extracted UI strings), so real row
boundaries were being silently merged/eaten.
RESOLUTION: read_tsv() now passes quoting=csv.QUOTE_NONE, which disables
special '"' handling entirely - correct for these files, which were never
quoted/escaped to begin with. Verified: 43670 rows now read back exactly
matching build_05_strings.py's own reported count and strings.tsv's real
line count.
Priority/value: this affected every check that reads *.tsv via read_tsv()
(not just the coverage summary line), so any future check added here
should NOT assume csv.DictReader's default dialect is safe for these
files - QUOTE_NONE is the correct dialect for all of this corpus's TSVs
unless a quoting/escaping convention is deliberately introduced later.
